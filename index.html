Hexagonal Architecture in NestJS

A way to organise a NestJS app so the business rules do not depend on Nest, Prisma or HTTP. This page follows one request, POST /users, through every file of the user module.

The problem it solves

Most Nest tutorials put everything in the controller or in a service that talks to Prisma directly. It works, and it ages badly. Here is the same endpoint written both ways.

Without Everything in one method


      
    
        
  • HTTP parsing, validation, database lookup, hashing and persistence live in one function.
    • 
        
  • Testing it needs a running Postgres.
    • 
        
  • The response returns the stored password hash.
    • 
        
  • A CLI command or queue consumer would copy the same rules.
    • 
        
  • Switching from Prisma to another ORM means editing controllers.
    • 
      

    

    

      
With Controller only translates

      

      
    
        
  • The controller makes no decisions. It converts HTTP into a call and the result back into HTTP.
    • 
        
  • The rules live in one place that any entry point can call.
    • 
        
  • The use case runs in a unit test with no database.
    • 
        
  • The response is a view that never contains the hash.
    • 
        
  • Prisma sits behind an interface and can be replaced.
    • 
      

    

  






  
The idea in one picture

  
Put the business in the middle. Everything that talks to the outside world plugs into the edge through an interface. The pattern is also called ports and adapters. Here it is with the real names from the user module.

  

    
  

  
The runtime path of POST /users

  

    Browser→
    UserController→
    CreateUserUseCase→
    UserRepository→
    PrismaUserRepository→
    Postgres
  

  
Read left to right, the call leaves the core through the right side. The imports do not follow it. PrismaUserRepository imports and implements UserRepository, so in the source code that arrow points back in. That reversal is the trick the whole pattern relies on, and the next section looks at the two sides separately.

  

    
Core
Entities, value objects and use cases in plain TypeScript. It would still compile if you deleted Nest, Prisma and Express.

    
Port
An interface the core owns. A driving port is what outsiders call, such as a use case. A driven port is what the core needs, such as UserRepository.

    
Adapter
Code that plugs into a port. A controller calls a use case. PrismaUserRepository implements UserRepository. Adapters can be swapped.

    
Dependency rule
Source code imports only point inward. The core never imports an adapter, even though at runtime it calls one.

  






  
Driving and driven

  
The two sides of the hexagon are not mirror images. On one side something calls the app. On the other side the app calls something. They are also named primary and secondary, or inbound and outbound.

  

    

      
Driving Someone calls the app

      
Something outside decides it is time to act and calls the application. The application never starts these conversations. It only answers them.

      

        
Also called
Primary or inbound. The left side of the picture.

        
Examples
HTTP controller, GraphQL resolver, CLI command, queue consumer, cron job, a test

        
The port
The use case itself. Its execute(command) method is the front door.

        
The adapter
Translates the outside format into a command and calls the port. Keep it thin.

        
In our module
user.controller.ts, create-user.dto.ts, create-user.command.ts

      

    

    

      
Driven The app calls out

      
To do its job the application needs something from the outside: storage, hashing, email, the clock. It asks through an interface and does not care who answers.

      

        
Also called
Secondary or outbound. The right side of the picture.

        
Examples
Database repository, password hasher, email sender, payment gateway, clock, event bus

        
The port
An interface the application declares, named after the need: UserRepository, not PrismaClient.

        
The adapter
Implements the port with a real technology. It can be swapped, and tests replace it with a fake.

        
In our module
user.repository.ts, password-hasher.ts, user.repository.impl.ts, bcrypt-password-hasher.ts

The one idea to take away. On the driving side the call and the import point the same way, so nothing special is needed. On the driven side they point opposite ways. The interface lives in the application and the adapter imports it, which turns the import around. That reversal is called dependency inversion.

The layers and what they may import

  
The whole pattern rests on the last two columns. If a file imports something from its forbidden column, the architecture is broken.

  

    

      
LayerContainsMay importMust never import

      
        
domainEntities, value objects, domain errorsOnly itself and shared/domainEverything else, including Nest and Prisma

        
applicationUse cases, ports (interfaces), views, mappersDomainPresentation, infrastructure, Nest, Prisma

        
infrastructurePrisma repository, bcrypt hasherApplication (to implement ports) and domainPresentation

        
presentationControllers, DTOs, HTTP validationApplication (use cases, views) and domain errorsInfrastructure

        
moduleWiring, the composition rootEverythingNothing. It is the one place allowed to know all layers.

      
    

  

  


presentation ──┐
               ├──▶ application ──▶ domain
infra ─────────┘

    
Read the arrows as "imports". Presentation and infrastructure both depend on application. Application depends on domain. Nothing depends on presentation or infrastructure, and that is why they can be replaced.

  






  
Folder structure

  
Each feature module repeats the same four folders. Anything used by several modules goes in shared/, which stays small and generic.


src/
├── shared/   shared kernel: small, generic, no module knowledge
│   ├── domain/           entity, value-object, aggregate-root, domain-event, domain-error, id
│   ├── application/      use-case, result, mappers/base.mapper, ports/ (logger, clock, event-bus, unit-of-work)
│   └── infrastructure/   config, logging, http (error handler), persistence/persistence-mapper
│
├── user/
│   ├── domain/
│   │   ├── user.entity.ts                      User with create() and reconstitute()
│   │   ├── username.ts, email.ts, password.ts  value objects that guard their own rules
│   │   └── user.errors.ts                      InvalidEmailError, EmailAlreadyUsedError, ...
│   ├── application/
│   │   ├── commands/create-user.command.ts     use case input
│   │   ├── views/user.view.ts                  use case output
│   │   ├── mappers/user-view.mapper.ts         User → UserView
│   │   ├── ports/user.repository.ts            what the use case needs from storage
│   │   ├── ports/password-hasher.ts            what it needs from a hasher
│   │   └── use-cases/create-user.use-case.ts   the "service"
│   ├── infrastructure/
│   │   ├── persistence/user.record.ts          DB row shape
│   │   ├── persistence/user-persistence.mapper.ts   User ↔ UserRecord
│   │   ├── persistence/user.repository.impl.ts implements the repository port with Prisma
│   │   └── security/bcrypt-password-hasher.ts  implements the hasher port
│   ├── presentation/
│   │   ├── dto/create-user.dto.ts              HTTP request, validation decorators
│   │   ├── dto/user-response.dto.ts            HTTP response, Swagger decorators
│   │   └── user.controller.ts
│   └── user.module.ts                         composition root: wires ports to adapters
│
└── product/   same shape as user/

    What you get for the effort: tests with no database
    
  
    Because the use case depends on interfaces, a test can hand it simple in-memory fakes. No Nest testing module, no Prisma, no Docker.
    
  
    
  
      
    
    • The test runs in milliseconds and reads like the business rule.
      • 
    
    • In production the same use case runs unchanged. Only the adapters differ.
      • 
    
    • A separate, slower test of PrismaUserRepository against a real database covers the adapter on its own.
      • 
  
    

    


    
  
    Ups and downs
    
  
    
    
    
      
    Ups
    
      
      
        
    • Rules in one place. You can read the domain without knowing Nest exists.
      • 
        
    • Fast, honest tests. Use cases run against fakes, so most of the suite needs no infrastructure.
      • 
        
    • Replaceable edges. Prisma to another ORM, bcrypt to argon2, REST to GraphQL, without touching the rules.
      • 
        
    • Several entry points. HTTP, a queue consumer and a CLI call the same use case.
      • 
        
    • Enforceable boundaries. A lint rule can fail the build when the domain imports infrastructure.
      • 
        
    • Independent shapes. The API contract, the database schema and the domain model can each change on their own schedule.
      • 
        
    • Parallel work. Agree on a port, then one person builds the adapter while another builds the use case.
      • 
      
    
    
    
    
    
      
    Downs
    
      
      
        
    • Many files. The first endpoint in the user module touches about 19 files, most under 20 lines. The second endpoint reuses much of that.
      • 
        
    • Mapping code. The same user exists as a DTO, command, entity, record and view, with mappers between them.
      • 
        
    • Indirection. "Go to definition" lands on an interface. Following a request means jumping between folders.
      • 
        
    • Learning curve. Port, adapter, driving, driven and composition root are new words for most teams.
      • 
        
    • Easy to hollow out. If entities become bags of getters and all logic sits in use cases, you pay the cost and lose the benefit.
      • 
        
    • ORM features. Lazy loading and relation helpers do not cross the repository boundary.
      • 
        
    • Only as strong as its enforcement. Without review or lint, imports drift and the layers blur.
      • 
      
    
    
    
  
    
  
    
    
    
      
    Reach for it when
    
      
      
        
    • The product will live for years and the rules will grow.
      • 
        
    • There is real business logic beyond saving and reading rows.
      • 
        
    • More than one entry point is likely: REST, events, jobs, CLI.
      • 
        
    • Several people work in the same codebase.
      • 
      
    
    
    
    
    
      
    Skip it when
    
      
      
        
    • It is a prototype, a script or a short-lived tool.
      • 
        
    • The app is plain CRUD with almost no rules.
      • 
        
    • The team is one or two people on a deadline and the schema is the model.
      • 
        
    • You can start with use cases and ports for the risky parts and grow from there.
      • 
      
    
    
    
  
    

    


    
  
    Questions you will get
    
  
    
    Isn't this just layered architecture?
    
    In classic layering each layer calls the one below, so the domain ends up depending on the database layer. Hexagonal inverts that. The interface (UserRepository) is owned by the application and the database code implements it. The core depends on nothing, and the database becomes a plugin.
    
  
    
  
    
    Is a use case the same as a Nest service?
    
    It does the same job as the service in a typical Nest app. The differences are that it is a plain class with no @Injectable(), it does one operation, and its input and output are explicit (a command in, a view out).
    
  
    
  
    
    Where does validation go?
    
    At three levels. The DTO checks the shape of the HTTP payload. The domain checks what a valid email or password means. The use case checks anything that needs data, such as whether the email is already taken.
    
  
    
  
    
    Why not return the entity from the use case?
    
    The entity carries the password hash and behaviour that callers should not depend on. A view is a small, stable contract made of primitives. The controller then needs no knowledge of domain internals, apart from domain errors.
    
  
    
  
    
    Where do transactions go?
    
    Declare a unit-of-work port in shared/application/ports. The use case wraps its steps in it, and the infrastructure implements it with something like prisma.$transaction. The use case never sees Prisma.
    
  
    
  
    
    How do we stop people from breaking the rules?
    
    Make the build fail. An ESLint rule per layer works, and dependency-cruiser can do the same with a dependency graph in CI.
